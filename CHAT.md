# Built-in text chat

Mutual acceptance in love/deep/buddy creates a connected pair, without collecting or disclosing WeChat. The existing pairing/quota/expiry algorithms remain unchanged. Pending recommendations cannot chat. Previously exchanged contacts remain available while their pair is active.

User entry: `/chat.html`; REST `/api/account/chat`; authenticated WebSocket `/api/chat/socket`. WebSocket authentication uses a first frame, never a token in the URL. Notifications carry only a refresh event; all content retrieval rechecks membership, connected state, blocks, bans, student verification and buddy-card deletion. Origin is checked against the request host. JWT expiry is checked at authentication and heartbeat. The browser retries and catches up through REST; visible-page polling also runs every 20 seconds.

Text only, 2,000 characters/message, 30 messages/minute/account. Client nonce prevents duplicate inserts after a network retry. Reads are paginated (50 messages) with monotonic per-user read positions. There are at most 3 sockets/account and 500 sockets/process; this is a protective limit, **not** a tested capacity claim. Only the latest 100 connected pairs per mode appear in the room list. Current deployment is a single app process; multiple replicas require a shared notification service. Requests use the existing global transaction lock, so larger concurrency requires benchmarking and reducing read-side contention.

WeChat is exchanged only after each participant separately submits their own contact and consent. Pending consent can be withdrawn; already disclosed information cannot be recalled. Closing/blocking prevents further reads/sends/contact display. It does not promise deletion of a recipient's saved information. Messages remain in MySQL; there is no automatic retention-period deletion in this release. Account deletion cascades the account's messages and contact submissions. Data is not end-to-end encrypted. Database backup/storage protection is the operator's responsibility.

Chat tables are excluded from the AI business-query allowlist. Administrators can access only submitted report evidence through `/admin-chat-reports.html`, including the reported message and preceding ten messages. Each access appends metadata to `.private/chat-review.jsonl`; no general administrator chat browsing endpoint exists. Report list is limited to the latest 100 reports.

Schema initialization creates additive `user_chat_*` tables. A transactionally guarded, one-time migration records historical contact exchanges; new accepted pairs no longer inflate contact-exchange statistics. Restart is safe and does not reclassify new chats as historical exchanges. Do not delete `user_chat_meta`. Backups must include these tables. Schema tables may remain during code rollback; never drop live messages to roll back a release.

Validation: isolated MySQL integration tests in `api/tests/chat-integration.cjs`; regression tests for weekly, deep and buddy pairing; browser checks for desktop/mobile sending, safe text rendering and consent. Tests use random, explicitly enumerated table prefixes and clean up only their own tables. Public WebSocket upgrade and HTTP authentication should be smoke-tested after deployment. Earlier 50-socket echo testing is not a full chat capacity benchmark.
